# SRX Address Books and Policy Ordering

A hands-on Juniper SRX lab covering Global Address Books, Address Objects, Address Sets, nested Address Sets, and Security Policy ordering.

This project builds on the earlier **SRX Advanced Security Policies** lab. It reuses the existing SRX environment and the DNS-deny policy created there to demonstrate how Address Set matching and policy order affect real traffic.

## Related lab

**Previous project:** [SRX-Advanced-Security-Policies](https://github.com/emadalshishani/SRX-Advanced-Security-Policies)

The previous project introduced the policy:

`internal-branch_ubuntu-user-test`

That policy matches the Ubuntu host `192.168.30.2/32`, matches DNS over UDP and TCP, and applies `deny`. It is an important part of the scenario in this repository: the new DNS permit policy initially remained ineffective while the previous deny policy was positioned above it.

The relationship is intentional. The earlier repository documents application-based matching and deny logging; this repository uses that existing rule as a real example of policy ordering and policy shadowing.

## Project objectives

- Organize IP addresses and subnets using the Global Address Book.
- Create Address Objects for individual hosts and networks.
- Build Address Sets from Address Objects.
- Build a parent Address Set containing nested child Address Sets.
- Use Address Sets as both source and destination match criteria in Security Policies.
- Observe first-match policy behavior.
- Demonstrate how a specific policy can be shadowed by an earlier broad policy.
- Verify the results using live traffic generated by Ubuntu and a second test host.

## 1. Global Address Book configuration

### Address Objects

The following objects were created:

```bash
set security address-book global address ubuntu-user-ip 192.168.30.2/32
set security address-book global address HQ-VLAN10-NET 192.168.10.0/29
set security address-book global address HQ-VLAN20-NET 192.168.20.0/29
set security address-book global address DNS-PRIMARY 8.8.8.8/32
set security address-book global address DNS-SECONDARY 8.8.4.4/32
```

The Ubuntu object already existed in the earlier lab; the command is shown here to present the complete logical Address Book used by this project.

### Child Address Sets

```bash
set security address-book global address-set VLAN10-SOURCES address HQ-VLAN10-NET
set security address-book global address-set VLAN20-SOURCES address HQ-VLAN20-NET
set security address-book global address-set VLAN30-TEST-HOSTS address ubuntu-user-ip
```

### Parent / Nested Address Set

```bash
set security address-book global address-set HQ-SOURCE-GROUP address-set VLAN10-SOURCES
set security address-book global address-set HQ-SOURCE-GROUP address-set VLAN20-SOURCES
set security address-book global address-set HQ-SOURCE-GROUP address-set VLAN30-TEST-HOSTS
```

`HQ-SOURCE-GROUP` contains three child Address Sets. As a result, a policy referencing this parent set can match addresses included through any of its child sets.

### Destination Address Set

```bash
set security address-book global address-set PUBLIC-DNS-SERVERS address DNS-PRIMARY
set security address-book global address-set PUBLIC-DNS-SERVERS address DNS-SECONDARY
```

The `PUBLIC-DNS-SERVERS` set groups `8.8.8.8/32` and `8.8.4.4/32`.

### Address Book verification

The configuration was checked on the SRX using:

```bash
show security address-book
```

The output showed all five Address Objects, the three child Address Sets, the parent `HQ-SOURCE-GROUP`, and `PUBLIC-DNS-SERVERS`.

## 2. DNS permit policy using Address Sets

A policy was created to permit DNS traffic from the nested source group to the DNS destination group:

```bash
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test match source-address HQ-SOURCE-GROUP
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test match destination-address PUBLIC-DNS-SERVERS
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test match application junos-dns-udp
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test match application junos-dns-tcp
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test then permit
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test then log session-init
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test then log session-close
```

### Why the first test remained blocked

Before applying the new Address Set policy, Ubuntu traffic was still being denied by the previous policy from the earlier repository:

`internal-branch_ubuntu-user-test`

The previous policy matched the Ubuntu source address and DNS applications, with destination address `any` and action `deny`.

The new permit policy was initially below that older deny policy. Since SRX security policies are evaluated in order and the first matching policy determines the action, the older deny policy handled the DNS requests before the new permit policy could be reached.

### Policy order correction

The new permit policy was inserted before the older Ubuntu DNS-deny policy:

```bash
insert security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test before policy internal-branch_ubuntu-user-test
```

After this ordering change, the Ubuntu host could resolve the reverse DNS names of both public DNS addresses, and the HTTPS request to Google succeeded.

### Before and after test results

**Before applying the new permit policy / while the old DNS deny policy was taking precedence:**

```text
$ ping 8.8.8.8
3 packets transmitted, 3 received, 0% packet loss

$ nslookup 8.8.8.8
;; communications error to 127.0.0.53#53: timed out
;; communications error to 127.0.0.53#53: timed out

$ nslookup 8.8.4.4
;; communications error to 127.0.0.53#53: timed out

$ curl -I https://google.com
curl: (6) Could not resolve host: google.com
```

**After inserting the Address Set DNS permit policy above the previous Ubuntu DNS-deny policy:**

```text
$ nslookup 8.8.8.8
8.8.8.8.in-addr.arpa    name = dns.google.

$ nslookup 8.8.4.4
4.4.8.8.in-addr.arpa    name = dns.google.
```

The HTTPS test also succeeded:

```text
$ curl -I https://google.com
HTTP/2 301
location: https://www.google.com/
content-type: text/html; charset=UTF-8
server: gws
```

**Testing note:** `nslookup 8.8.8.8` and `nslookup 8.8.4.4` perform reverse DNS lookups for the IP addresses. The successful `curl` request to `google.com` is the accompanying evidence that the hostname could be resolved and an HTTPS request could be made.

## 3. ICMP deny policy using Address Sets

A separate policy was created to deny ICMP Echo Request traffic from the nested source group to the public DNS address group:

```bash
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test_ping_Deny match source-address HQ-SOURCE-GROUP
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test_ping_Deny match destination-address PUBLIC-DNS-SERVERS
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test_ping_Deny match application junos-ping
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test_ping_Deny then deny
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test_ping_Deny then log session-init
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test_ping_Deny then log session-close
```

### Why the first ICMP deny test did not work

The lab already had a general policy named `internal-branch`:

```text
policy internal-branch {
    match {
        source-address any;
        destination-address any;
        application any;
    }
    then {
        permit;
    }
}
```

The ICMP deny policy was initially positioned after this broad permit policy. ICMP traffic matched the general `any/any/any` permit policy first, so the later specific deny policy was not reached.

### Policy order correction

The ICMP deny policy was inserted before the broad permit policy:

```bash
insert security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-address_set_test_ping_Deny before policy internal-branch
```

This placed the specific ICMP deny rule ahead of the general permit rule.

### ICMP test from PC2 (192.168.10.3)

Before the ordering correction, PC2 successfully pinged `8.8.8.8`:


### Ubuntu verification after the ICMP deny policy

```text
$ ping 8.8.8.8
2 packets transmitted, 0 received, 100% packet loss

$ nslookup 8.8.8.8

$ curl -I https://google.com

```

These results show the intended separation of application behavior: ICMP Echo Requests to the DNS server addresses were denied, while DNS reverse lookup and HTTPS access continued to work.

## 4. Policy ordering and policy shadowing

This lab demonstrates two distinct ordering problems:

| Scenario | Specific policy | Earlier policy that shadowed it | Correction |
|---|---|---|---|
| DNS permit | `internal-branch_ubuntu-user-address_set_test` | Previous Ubuntu DNS deny policy, `internal-branch_ubuntu-user-test` | Insert the DNS permit before the old DNS deny |
| ICMP deny | `internal-branch_ubuntu-user-address_set_test_ping_Deny` | General `internal-branch` policy matching any source, destination, and application with permit | Insert the ICMP deny before `internal-branch` |

The key principle is that a policy can be correctly configured and still not produce the expected result if an earlier policy matches the same traffic first.

Specific policies should be placed before broader policies when the intended behavior requires the specific rule to take precedence.

## 6. Key takeaways

- Address Objects provide named references for individual hosts and networks.
- Address Sets group multiple Address Objects.
- Nested Address Sets allow a parent group to contain several child groups.
- The same parent Address Set can be reused as a policy source match.
- Destination Address Sets can group multiple permitted or restricted destinations.
- Policy ordering directly affects which action is applied.
- A broad `any/any/any permit` rule can shadow a more specific deny rule placed beneath it.
- A specific DNS permit policy must be placed before an earlier DNS deny policy when it is intended to allow that traffic.
- Policy configuration should be validated with traffic tests and SRX verification commands.
